\section{Chapter 1 --- Introduction} \hfill [p: 8-10]
\label{sec:intro}

\subsection{1.1 Background} \hfill [p: 2-3]
\begin{itemize}
    \item Growth of cloud computing in recent years.
    \item Multi-cloud and hybrid-cloud adoption in large enterprises; drivers
          (data residency, legacy on-prem systems, cost, resilience).
    \item Security challenges specific to the hybrid model (split trust boundary,
          heterogeneous control planes).
    \item The shift-left / DevSecOps trend and the rise of AI-assisted code generation.
\end{itemize}

\subsection{1.2 Research Challenges in Hybrid Cloud} \hfill [p: 1-2]
\begin{itemize}
    \item Weak security linkage between public and private cloud.
    \item Absence of a clear, repeatable security process across the two sides.
    \item Fragmented, disconnected security tooling with inconsistent outputs.
    \item Misconfiguration risk amplified by fast, AI-generated IaC.
\end{itemize}

\subsection{1.3 Research Gaps} \hfill [p: 1]
\begin{itemize}
    \item Few papers propose or build an end-to-end security \emph{process} for hybrid cloud.
    \item Tool integration is hard; findings from different tools need a unified,
          quantitative score rather than isolated pass/fail signals.
    \item Deployment context (exposure, cost) is rarely folded into prioritization.
\end{itemize}

\subsection{1.4 Research Objectives} \hfill [p: 1]
\begin{itemize}
    \item O1: Propose a pipeline that links security across public and private sides
          of a hybrid cloud.
    \item O2: Propose a risk-scoring method that aggregates heterogeneous tool findings.
    \item O3: Build a reference system implementing the pipeline.
    \item O4: Evaluate the reference system across 2 scenarios.
\end{itemize}

\subsection{1.5 Contributions} \hfill [p: 1]
\begin{itemize}
    \item C1: A reusable SysSecOps \emph{pipeline/architecture} with a security gate
          placed between IaC synthesis and deployment, applied uniformly to both the
          AWS (CDK) and on-prem (Ansible) sides.
    \item C2: A reference \emph{system} implementing the pipeline (AI generation +
          regen feedback loop, multi-scanner gate, risk scoring, deploy governance,
          operational monitoring, CLI + Streamlit UI).
    \item C3: A quantitative, deduplicated, ML-augmented \emph{risk-scoring engine}.
    \item C4: A \emph{systematic evaluation} over 2 scenarios (correctness, scoring
          behavior, deployment, and observability).
\end{itemize}

\subsection{1.6 Thesis Structure} \hfill [p: 0.5]
\begin{itemize}
    \item One paragraph mapping each remaining chapter.
\end{itemize}

\section{Chapter 3 --- System Architecture} \hfill [p: 12-15]
\label{sec:arch}

\subsection{3.1 Design Goals and Requirements} \hfill [p: 2]
\begin{itemize}
    \item Gate before deploy; uniform engine for both hybrid sides; graceful
          degradation; auditability; feedback-driven remediation.
\end{itemize}

\subsection{3.2 Three-Zone Reference Architecture} \hfill [p: 4-5]
\begin{itemize}
    \item High-level flow diagram (generate -> synth -> gate -> decision -> deploy -> monitor)
          and the module-to-zone mapping table (generation/, security\_gate/,
          pipeline/, scripts/, monitoring/).
    \item \textbf{Zone 1 --- AI + IaC Local Dev (detailed).} Natural-language prompt intake;
          provider abstraction (Bedrock Qwen3-Coder / OpenRouter); single-stack CDK app
          synthesis under a hardened system prompt (least-privilege IAM, default
          encryption, no public SSH/RDP, RETAIN for stateful resources); local
          pre-validation via \texttt{cdk synth}/\texttt{cdk diff}; artifacts written to
          \texttt{generated\_cdk/} and \texttt{logs/}. Maps to \texttt{generation/},
          \texttt{generated\_cdk/}.
    \item \textbf{Zone 2 --- IaC Security Gate (detailed).} The chokepoint between
          \texttt{cdk synth} and \texttt{cdk deploy}. Scans the \emph{synthesized}
          CloudFormation (not CDK source) with four pluggable adapters (Checkov,
          cfn-lint, Infracost, AWS Config) plus an internal heuristic analyser;
          cross-source deduplication by \texttt{(resource\_id, template, category)};
          additive risk scoring with cost and live-compliance dimensions; emits a
          \texttt{pass}/\texttt{review}/\texttt{reject} decision via \texttt{can\_deploy()};
          persists an append-only gate report and approval/rejection audit records with
          the approver's STS identity. Maps to \texttt{security\_gate/},
          \texttt{pipeline/}, \texttt{scripts/}. The risk-scoring engine sits at the
          Zone 1/Zone 2 boundary (forward reference to Chapter 5).
    \item \textbf{Zone 3 --- Hybrid Infrastructure and Ops Monitoring (detailed).}
          The AWS (CDK-provisioned) side and the on-prem (Ansible-managed) side, plus
          the operational monitoring loop. Post-deploy telemetry publishing (SSM Parameter
          Store, EventBridge \texttt{GateDecision} events, CloudWatch metrics/logs/alarms),
          three-layer security monitoring mesh (Application Insights; per-resource
          operational + security alarms; CloudTrail CIS alarms + VPC flow-log alarms),
          and event-driven drift/rollback remediation via the ops-loop Lambda. Maps to
          \texttt{monitoring/}, \texttt{pipeline/}. Detailed tool inventory and
          public/on-prem connectivity are covered in 3.4.
\end{itemize}

\subsection{3.3 End-to-End Data Flow} \hfill [p: 2-3]
\begin{itemize}
    \item Artifact lifecycle: prompt -> generated code -> synthesized template ->
          findings -> score -> decision -> approval/rejection record -> deployment ->
          telemetry.
\end{itemize}

\subsection{3.4 Hybrid Deployment Topology and Zone 3 Tooling} \hfill [p: 3-4]
\begin{itemize}
    \item \textbf{Zone 3 tool inventory (explicit).} AWS side: CloudFormation/CDK,
          CloudWatch (metrics, logs, alarms, dashboard), SSM Parameter Store,
          EventBridge, SNS, Application Insights, CloudTrail (+ S3 CIS alarms),
          VPC flow logs, AWS Config, and the ops-loop Lambda. On-prem side: Ansible
          (playbook synth-check / \texttt{--check} dry run), SSM Agent for managed-instance
          registration, and the same gate/scoring engine applied to Ansible artifacts.
    \item \textbf{Public $\leftrightarrow$ on-prem connectivity (list the methods).}
          Mesh-overlay VPN (WireGuard/Tailscale) forming the hybrid trust boundary;
          AWS Systems Manager hybrid activations registering on-prem nodes as
          SSM managed instances; EventBridge/SNS as the cross-side event and
          notification plane; SSM Parameter Store as the shared state channel. Describe
          which channel carries control, telemetry, and remediation traffic.
    \item Current implemented subset vs. conceptual full topology (CDK-first implemented;
          Ansible/on-prem path defined in the model).
\end{itemize}

\subsection{5.2 Proposed Multi-Factor Formulation} \hfill [p: 2-3]
\begin{itemize}
    \item Severity, exposure, exploitability, confidence, cost; weighting scheme.
\end{itemize}

\subsection{5.3 Implemented Additive Scoring} \hfill [p: 2]
\begin{itemize}
    \item Severity points (Critical 20 / High 10 / Medium 5 / Low 1), cost bands
          (Infracost monthly delta: $>\$50\to10$, $>\$10\to5$), config-violation points
          ($5\times$ AWS Config violations), ML points; thresholds
          (\texttt{pass\_max}=20, \texttt{review\_max}=80).
    \item Decision function: $0\text{--}20$ \texttt{pass}, $21\text{--}80$ \texttt{review},
          $>80$ \texttt{reject}; relationship between the proposed model and the
          implemented additive approximation.
    \item \textbf{Clarify how scoring plugs into the gate} (score components object,
          provenance/override flags, report schema fields consumed by \texttt{can\_deploy()}).
\end{itemize}

\subsection{5.4 ML Code-Risk Model --- Dataset and Training} \hfill [p: 3-4]
\begin{itemize}
    \item \textbf{Dataset construction (make explicit).} Source corpus of secure/insecure
          code samples, labelling scheme, and the merge step
          (\texttt{dataset.csv}/\texttt{dataset.jsonl}/\texttt{dataset\_with\_risk.csv});
          class balance and train/test split.
    \item \textbf{Feature extraction.} Static-analysis signals from Bandit and Semgrep
          (issue counts by severity/confidence, rule categories) forming the feature
          vector; \texttt{feature\_importance.csv} for interpretability.
    \item \textbf{Training procedure.} Logistic-regression training
          (\texttt{LogisticRegression.py}), hyperparameters, evaluation metrics
          (accuracy/precision/recall/AUC), and model persistence.
    \item \textbf{Training/inference parity.} The gate adapter recomputes the identical
          Bandit+Semgrep features at inference time; probability-to-points mapping into
          the additive score.
\end{itemize}

\subsection{9.2 Limitations and Threats to Validity} \hfill [p: 2-3]
\begin{itemize}
    \item Single-stack generation assumption; multi-stack apps out of scope.
    \item Additive vs. full multi-factor scoring: exposure/exploitability/confidence
          modelled conceptually but not yet wired into gate weights.
    \item Heuristic coverage defers breadth to Checkov; novel resource types depend on
          external tools.
    \item Cost-estimation fidelity: Infracost conservative for usage-based resources.
    \item Ansible/on-prem (Zone 3 hybrid) path implemented for the CDK/AWS subset only.
    \item No formal benchmark: demonstrative, artifact-based evaluation rather than a
          controlled study against a labelled misconfiguration corpus.
    \item ML dataset scope/bias; scenario count; single-cloud focus.
\end{itemize}

          deployment-context exposure into the gate.
    \item Confidence weighting to down-weight low-confidence findings.
