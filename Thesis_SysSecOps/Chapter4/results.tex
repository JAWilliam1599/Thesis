\subsection{RQ2: Cross-Boundary Enforcement Equivalence}
\label{subsec:results-rq2}

No run in either arm recorded a failure of any attempted checkpoint; all 65 runs
were classified in the failure class \texttt{none}. Three observations from the
live arm carry more weight than the rates themselves, because the offline
campaign structurally could not produce them.

First, apply is not merely a zero exit code. A separate playbook reads the
resulting state back off the host and asserts against it: that the service
directory exists with mode \texttt{0750} owned by the service account, that the
configuration file exists with mode \texttt{0640}, that the account exists with a
non-interactive shell, and that the deployed configuration binds the service to
the loopback interface. Its expected values are written literally rather than
read from the fixture's variables. Nine assertions executed with zero failures on
every apply run.

Second, idempotency is measured rather than assumed. Each \\ \texttt{ans-pass-deploy}
run applies the playbook a second time and parses the resulting \texttt{PLAY
RECAP}; all three recorded \texttt{changed=0}, so the converged state is stable
under re-execution.

Third, the three \\ \texttt{ans-reject-deploy-blocked} runs requested deployment
explicitly and never received one. Their recorded stage sequences terminate after
\texttt{ansible.gate}: no dry run, no apply, no verification. The reject
decision blocked deployment against a live, reachable, credential-verified host
rather than in simulation.

The run counts bound how far these results reach. The last four checkpoints in
Table~\ref{tab:rq2-checkpoints} rest on three runs each, executed against one
host running one operating system image from a fresh boot. Three successes show
that the apply, verification and idempotency machinery works and produces the
records it claims to, and that the gate stops a rejected change at a live host.
They are far too few to characterise how often any of it fails, or to speak to
host heterogeneity, concurrent targets, or partial failures.

\subsubsection{Detection Coverage Across the Boundary}
\label{subsec:evaluation-results-parity}

Checkpoint attainment shows that the on-premises path \emph{runs} the same
workflow. Whether it \emph{sees} the same things is the question on which RQ2
turns, and it is measured as detection coverage rather than as decision
equality, for the reasons given in
Section~\ref{subsec:evaluation-rqs}. For each matched pair, did the branch emit
a finding whose category names the weakness the fixture encodes? The criterion
is applied identically to both branches, and a generic style finding that
happens to touch the same artifact does not count as detection.

The measurement is taken twice over the eleven weakness classes derived in
Section~\ref{subsec:evaluation-rq2}. The \emph{baseline} arm was run with the
gate frozen before any fixture had been inspected for whether it would be
detected; the \emph{remediated} arm was run after detection rules were written
for the gaps the baseline exposed. Each arm is 72 runs. The class list, the
fixtures and the matchers were identical in both arms, and the baseline was
never recomputed after the rules were added. Table~\ref{tab:rq2-coverage}
compiles both arms from the gate reports referenced by each run record.

The baseline misses are not all the same kind of failure. Most are genuine blind
spots: no component in that branch inspected the construct at all, so no wording
of the criterion would have credited a detection. One is not. On the cloud
\texttt{incorrect-permissions} fixture the baseline report contained exactly one
finding --- \texttt{CKV\_AWS\_33}, ``Ensure KMS key policy does not contain
wildcard (*) principal.'' The scanner saw the weakness, but the finding carried
no category naming the class, and the pre-registered matcher for CWE-732 did not
recognise Checkov's phrasing, so the run counted as undetected. The matcher was
left frozen and the gate was given a rule that emits
\texttt{permissive\_resource\_policy} directly, fixing the vocabulary at the
producer rather than at the reader.

The baseline left ten gaps in total --- four on the cloud branch and six
on-premises --- and the remediated arm closed nine of them: six rule families
were added to the on-premises configuration adapter and three to the cloud
template analyser, each emitting a category already in the pre-registered list
for its class. Coverage rose to $10/11$ in the cloud and $11/11$ on-premises,
and the cross-tabulation collapsed from eight discordant classes to one. Both
specificity controls --- a compliant CDK stack and a compliant playbook, run in
the same campaign --- remained silent on every one of the eleven classes in both
arms, so the added rules respond to the weakness rather than to the fixture.

What the remediated arm does \emph{not} establish is general recall. It measures
the same eleven classes the baseline located, after targeted repair, so $10/11$
answers ``were these gaps closable within this architecture?'' and not ``how much
does this gate see?'' The baseline is the arm that carries evidential weight
about the system as it stood; the remediated arm shows what closing the baseline
gaps cost, which was nine rule families in two files.

Three limits bound how far these numbers should be read. The fixtures are
author-written, so a class counts as covered when the gate names a weakness the
author composed to be namable; the figures measure rule-to-CWE alignment rather
than field recall. The controls establish that no matcher responds to a compliant
artifact, but a control that produces no findings cannot establish that a matcher
will refrain from firing on an \emph{unrelated} finding in a busier report. And
any observed gap is a property of the particular scanner set assembled in this
prototype, not of the process architecture.

The substantive result survives all three. Where a class is named on both sides,
the identifiers are the same on both sides, because the on-premises rules were
written to emit the cloud-side categories. A weakness therefore carries one name
across the boundary, and both branches deduplicate and score it through a single
code path. Without that shared vocabulary the columns of
Table~\ref{tab:rq2-coverage} would not be comparable at all.

\subsection{RQ3: Unified Risk-Evaluation Capability}
\label{subsec:results-rq3}

\subsubsection{Dataset Composition}
\label{subsubsec:results-dataset}

The corpus was constructed from two classes of Python files. Approximately 800 positive
examples were selected from SecurityEval and PyCode-Vul \cite{siddiq2022seceval, karim2025benchmark}. Vulnerability categories that could not be
represented by the configured Bandit and Semgrep features were excluded from the model
corpus. The negative reference class contained approximately 800 files sampled from PyCode-Vul \cite{karim2025benchmark} and
maintained Python projects, including \texttt{click}, \texttt{rich}, and
\texttt{typer}.

The negative examples are referred to as \emph{reference secure} files rather than
formally verified secure files. Maintained project code can still contain unknown
vulnerabilities, and the assigned negative labels therefore represent a practical
reference assumption. Similarly, excluding vulnerability categories outside the
observable scope of the selected analysers narrows the interpretation of the results.
The reported performance applies to the retained, detector-visible subset and is not an
estimate of performance over the complete SecurityEval dataset.

The held-out test partition contained 324 samples: 162 negative samples and 162 positive
samples. The balanced distribution limited the influence of class frequency on the
reported accuracy.

\subsubsection{Per-File Risk Records}
\label{subsubsec:results-per-file}

In addition to the aggregate classification measures, the corpus is reprocessed through
the trained component to obtain a predicted probability and risk contribution for each
file. The resulting machine-readable artifact is archived with the project repository
for inspection and reproducibility. Each record contains the sample identifier, dataset
source, assigned label, extracted feature values, predicted probability, predicted
class, and learned risk contribution. When the complete set of gate inputs is available,
the record also contains the component scores, total score, and resulting deployment
decision.
